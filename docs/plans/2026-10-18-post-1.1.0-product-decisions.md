# Post-1.1.0 product decisions — YouTube duration cap, first-load performance, cloud sync

Date: 2026-10-18 · Baseline: v1.1.0 (`7d610ad` + post-release commits)
Status: YouTube cap **implemented**, logo **optimized**, cloud sync **deferred with a
recommended path**, remaining perf work **scoped**.

This doc records the decisions made in the E track of the post-1.1.0 cleanup so
the next session does not re-litigate them.

## 1. YouTube 10-minute cap — implemented (best-effort, keyless)

**Problem.** `MAX_DURATION_SEC = 600` was only enforced for an explicit
`?start=&end=` clip range. A 40-minute video pasted without those params
passed the gate and could trigger a Gemini call (cost + long transcripts).

**Constraint.** The free `oEmbed` endpoint exposes no duration, and the IFrame
Player's `getDuration()` is only available after a player loads — which is why
the old comment said the general case was unenforceable without the paid Data
API.

**Implementation.** `static/js/modules/youtube/duration.js` creates a hidden
1×1 IFrame Player at parse time, reads `getDuration()` on `onReady`, then
destroys it. `static/js/modules/youtube/index.js` awaits the probe after oEmbed
metadata and before rendering any tab; over-cap videos show an error and never
reach a Gemini-calling tab. Parse button is disabled with a `…` label while the
probe runs.

**Properties / limits**

- Probe timeout 8 s; any failure (offline, blocked iframe API, embed-disabled,
  geo-blocked) resolves `null` → **falls back to the old clip-range gate** and
  lets the user proceed. Fail-open, never a hard block.
- Adds one hidden player load (~1–2 s typical, up to 8 s worst case) to every
  paste. Only the first tab render waits; nothing else in the app is affected.
- Hidden player counts as an embed view. No Google API key is involved.
- The probe reuses `window.YT` if the companion tab already loaded it, and
  chains `onYouTubeIframeAPIReady` so both loaders coexist.
- Tests: `static/js/modules/youtube/duration.test.html` (cap boundaries,
  `formatDurationMmSs`, empty-id guard). The probe itself is not unit-testable
  offline; keep it manually verified when touching the panel.

**Follow-up (optional).** Pass the probed duration into the tabs so the
companion tab can show "duration 12:34 · over the 10-min AI cap" instead of a
generic error, and reuse it for the estimate in the import tab.

## 2. First-load performance — measured, quick win shipped

Measured 2026-10-18, headless Chromium 1440×900, `python3 -m http.server`,
cold context (localhost — treat absolute times as a lower bound; bytes are the
network-independent part):

| Metric | Value |
|---|---|
| Resources / transfer / decoded | 80 / **2.89 MiB** / 14.2 MiB |
| DOMInteractive / DOMContentLoaded | 129 ms / 513 ms |
| `window.documentManager` ready | **623 ms** |
| First analyzed content rendered | 625 ms |

Top costs:

| Asset | Transfer | Why it loads at boot |
|---|---|---|
| `libs/dict/base.dat.gz` + `check.dat.gz` + `cc.dat.gz` + `tid.dat.gz` + `tid_map.dat.gz` | **≈ 11.5 MiB** | boot auto-analysis → `initSegmenter()` → kuromoji builder |
| `static/logo.png` | **1.19 MiB** | 1024×1024 PNG displayed at 22×22 px |
| `libs/easymde/easymde.min.js` + CSS | ~345 KiB | classic `<script>` at boot, only needed when editing |

**Root cause of the dictionary load:** `main-js.js:4943` schedules
`setTimeout(() => analyzeText(), 100)` on boot. `analyzeText` calls
`initSegmenter()`, whose first call builds the kuromoji tokenizer and pulls the
five dictionary files. The tokenizer is already lazy with respect to user
actions; the eager part is the **boot auto-analysis**.

### Decisions

1. **Logo — shipped.** Re-encoded `static/logo.png` from 1024×1024 (1,217,716 B)
   to 128×128 optimized PNG (**20,776 B, −98.3%**). It is displayed at 22 px
   (128 px is >5× for retina) and also serves as `login.html` favicon. No markup
   change. Removes ~1.2 MiB from every cold load.
2. **Boot auto-analysis — switch shipped (2026-10-18 second pass).** The
   automatic run waits for `load` + idle, and is skipped on data-saver/2G.
   An A/B switch now selects the mode instead of hard-coding it:
   `localStorage['yomikikuan_boot_analysis']` / `config.js:bootAnalysisMode`
   = `immediate` (legacy +100 ms) | `idle` (default) | `manual` (no
   auto-run; renders a prompt + Analyze button). `manual` is the
   interaction-gated behaviour (~11.5 MiB saved for users who never
   analyze); AB can flip `config.js` without a code change.
3. **EasyMDE lazy-load — shipped (2026-10-18 second pass).** The bundle is
   injected after the load event via idle callback on normal connections, and
   only on first interaction for data-saver/2G. The textarea keeps native
   behaviour until mount through value/focus/addEventListener shims; buffered
   input/focus/blur handlers are re-attached to CodeMirror. Covered by E2E
   ⑨/⑩. Failure to fetch the bundle is fail-open (plain textarea remains).
4. **Hosting compression — infra.** All dictionary files are already gzip; a
   Brotli-capable host typically saves ~20–25% more. No code change.
5. **Do not** block on the PWA precache list: `static/pwa-assets.json` (~14 MB)
   is only downloaded when the user explicitly clicks 安装, not on boot.

**Recommended order:** logo (done) → easy MDE lazy-load → decide on boot
auto-analysis → re-measure on a throttled mobile profile.

## 3. Cloud sync (Firestore) — Option A shipped; Firebase adapter config-gated

Current state: `login.html` does Google OAuth via Firebase and writes to
Firestore; there is **no automated test** for the sync path, and the merge
semantics are implicit. The rest of the app is local-first
(`localStorage` + IndexedDB SRS), so a wrong sync design can destroy
user-owned data (documents, SRS review state).

Risks: bidirectional overwrite on multi-device login; offline edits queued or
lost; auth-token expiry mid-sync; partial batch writes; SRS rows merged by id
in backups but *not* obviously in Firestore.

Options:

| Option | Behaviour | Risk |
|---|---|---|
| **A. Backup-only (recommended first step)** | explicit Push / Pull buttons, no background sync; conflict → prompt "cloud is newer, overwrite local?" | low |
| B. Last-write-wins per document | background sync by `updatedAt`; silent overwrite | medium (data loss) |
| C. Per-document version vectors + merge UI | true multi-device merge | high effort |

**Status (2026-10-18 third pass): Option A is implemented app-side.**
`modules/cloud-sync/index.js` (+152 unit cases) implements explicit Push /
Pull with the conflict prompt described above, against the documented
`window.__yomikikuanCloudBridge` contract; user-menu Push/Pull buttons are
wired. E2E ⑫ covers push / pull / conflict accept+dismiss / missing-bridge
with a mock bridge.

**Update (2026-10-21): Firebase adapter shipped, config-gated.** The dead
Firestore merge path (`performDataSync`, auto-sync subsystem, `firebaseSignOut`
guards, header sync button) was **deleted** (−408 lines total). The new
`modules/cloud-sync/firebase.js` lazily imports Firebase v10.14.1 and installs
the bridge when `config.js` provides `firebaseConfig`; without a config it
fetches nothing and keeps the "not configured" behavior. 134 mock-SDK tests +
E2E ⑬ (SDK-load failure) cover the app side.

**Still open — real Firebase verification.** No project/emulator is available
in this environment, so the following are mocked only: actual gstatic module
CORS, Anonymous provider enablement/token refresh, Firestore rules
enforcement, real `Timestamp` instances, offline retry and multi-device
anonymous-uid semantics (anonymous uid is per-browser; clearing site data
orphans the cloud copy). Setup steps (project, Anonymous auth, rules,
emulator) are in `config.example.js` / the module header.
